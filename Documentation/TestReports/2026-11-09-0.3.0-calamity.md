## Findings

1. **Calamity roughly doubles main-thread CPU work in the idle scene:** draw + update ≈ 1.28 → 2.23 ms per frame.
   This is still ≈ 13 % of a 16.7 ms frame, so FPS is unaffected here (vsync-limited).
2. **The largest single increase is player update (+0.19 ms per update, ×4.5).** This phase includes every mod's
   per-player hooks; with only Calamity added, the increase is attributable to Calamity's player logic as a whole,
   but not to a specific Calamity system. Next largest: work outside the entity phases (+0.10 ms), projectiles, NPCs.
3. **Calamity doubles the managed allocation rate (+5.9 MB/s)** and GC frequency; GC pause time ≈ 16 ms per minute.
4. **Draw CPU p95 rises by 74 %** — the heavy frames of the 4-frame render cycle become heavier.
5. **Memory after unloading Calamity stays high:** in session B, TPO-only runs after unloading Calamity show a working set
   of 2.33 GB, while fresh TPO-only sessions earlier the same day showed 0.95–1.24 GB (different resolution, so not an
   exact comparison). Managed heap is back to ~0.65 GB, so the retained memory is mostly native/non-heap. Unloading does
   not return all memory. **Memory comparisons therefore need a fresh game launch per mod set**; CPU metrics are fine
   within one session.
6. No errors and clean unload/reload with Calamity 2.2.4 + Calamity Music 2.1.

## What TPO can and cannot do about this

TPO's rules (CLAUDE.md, Plan 02) exclude patching Calamity's own code without strong evidence and approval. These idle
results show no frame-time problem to fix. The next step is a heavy, repeatable scenario (boss/event with many NPCs
and projectiles) to see whether the per-player cost, projectiles or GC turn into frame-time problems there.
